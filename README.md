# CarbonOS Sugar (prototype)

Traceable carbon accounting and energy-performance insights for sugar mills.
A time-boxed **prototype** of the workflow described in the CarbonOS Industrial research deck, narrowed to sugar
production. **Not validated in an operating mill, not independently verified or certified.**
All bundled data is **FICTIONAL**.

## Problem
Electricity bills, fuel logs and production records are fragmented, so an emissions figure is hard to review if its
source cannot be traced. CarbonOS Sugar turns activity records into a reviewable inventory where every number links
back to its record, factor, formula, units and provenance.

## Features (all implemented and covered by tests)
* Factory and reporting-period setup with a visible boundary; optional declared exclusions
* Manual entry and CSV import (preview, row-level errors, nothing dropped silently)
* Emission-factor library with status/provenance; illustrative factors blocked in real-reporting mode
* Exact-decimal, unit-validated calculation engine (separate from the UI)
* Missing data / missing factor / unsupported category stay **unresolved — never zero**
* Partial totals are labelled **partial**; incomplete inventories cannot look complete
* Factory-wide energy intensity (kWh/t cane, kWh/t sugar, L diesel/t cane) where data supports it
* Transparent anomaly flags and observation-based (or labelled generic) recommendations
* Reverse traceability: pick any result → activity, factor snapshot, formula, conversion, provenance, timestamp,
  engine version, snapshot ID, re-computation check
* Immutable calculation snapshots, stale detection, snapshot comparison, audit history
* CSV exports, Markdown report and ZIP bundle built from the stored snapshot

## Stack
Python 3.10+ · Streamlit · SQLite · pandas · pytest (tested with Python 3.12, Streamlit 1.66.1, pandas 3.0–3.1)

## Install and run
```bash
git clone <repository-url>
cd carbonos-sugar
python -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
pytest                              # run tests
streamlit run app.py                # launch
```
The database is `carbonos.db` in the working directory (override with `CARBONOS_DB=/path/file.db`).

## Demo data
* In the app: **Setup → Load synthetic demo dataset** (tick *skip current-period records* to practise the CSV import).
* Or `python seed_data.py` (add `--no-current-records` to skip the current period's records).
* Demo hand-check: electricity 46,000 kWh × 0.70 = 32,200 kg; diesel 800 + 750 L + 0.9 kL (=900 L) × 2.50 = 6,125 kg;
  partial assessed total **38,325 kg = 38.325 t CO₂e** — fictional numbers with illustrative factors.
* `sample_data/exports/` holds real exports generated by the app from that demo (still fictional).

## CSV format
```csv
activity_date,category,activity_name,quantity,unit,source_reference,provenance,notes
2026-01-01,purchased_electricity,Grid electricity,12500,kWh,DEMO-BILL-001,synthetic_demo,Fictional demonstration record
```
Required: `activity_date, category, activity_name, quantity, unit, provenance`. Provenance for activity data:
`user_provided`, `synthetic_demo`, `unknown`. Valid categories and units are listed on the CSV import screen and in
`METHODOLOGY.md`. `sample_data/demo_activities_with_errors.csv` demonstrates every rejection type.

## Methodology, provenance and factor policy
See [METHODOLOGY.md](METHODOLOGY.md). In short: **no real emission factors are bundled**; real reporting requires
factors you source and verify (CEA CO₂ Baseline Database, TERI sugar report and GHG Protocol are starting points,
not proof of any value).

## Limitations
No real-mill validation or partner; bagasse/biogenic, wastewater, stage allocation, product footprints, Scope 3 are
not implemented; single-user local SQLite; audit history is not tamper-proof. Demo video link: _not yet recorded_.

## Roadmap (not implemented)
Verified India-specific factors; by-products (ethanol, jaggery) with allocation; biogenic/bagasse treatment;
wastewater; sub-meter data; React/FastAPI/PostgreSQL migration; field validation with a partner mill.
